## The product target

A polished fixed-view pirate village with substantial buildings, readable stone/wood/metal, navy roofs and warm brass, soft ground contact, raised grass/cliff edges, lush but deliberate scenery, coherent paths/water and a usable building interface. Walls must be placeable on approved valid grid cells, connected into useful defenses, upgradable under real rules, attacked or bypassed according to actual pathing, and visibly breached/restored at the real state.

The supplied reference sets the visual direction. The English target concept adds wall examples; it does not validate exact tile locations, inventory, a usable pier or transactions. Passing a palette/color check alone is insufficient. Actual running-game quality and functional acceptance are separate gates.

## Recommended first-release assumptions

- Keep the existing 0.5 world-unit grid and 2×2 wall segment footprint for the first contract unless a reviewed compatibility decision changes them.
- Start with the current twelve stable wall IDs. A larger target allowance is selected only through its complete bounded cohort path; illustrated bricks are not inventory IDs.
- Reuse existing single-wall levels 1–5, base HP 60/120/200/300/420, prices 10/20/40/80/160, campaign unlocks and actual payer/skill/recovery modifiers. No second economy, automatic upgrade timer or implicit repair is added.
- Preserve the current distinction between hostile boarder blocking and friendly captain/projectile behavior until WALL-01 explicitly decides otherwise. No hidden gates or new captain colliders are assumed.
- Keep solo/highscore behavior and current authority. BASE-45 owns the separate reset/record-continuity issue; wall work cannot claim to have fixed it.

These are proposed implementation defaults, not a replacement for the small reviewed contracts. Exact actor, coastal support, unbuilt reservation, version carrier and selected allowance choices have named owners and observable tests.

## Parallel assignment after the shared gate

Use separate clones and one writing agent per branch. A suggested initial split is civil buildings, core defense art, other defense/wall art, ground/water, nature/composition, and Move presentation, with one coordinating integrator. Server wall-rule/legacy/client work and canonical transaction work have separate bounded owners. More detail: [PARALLEL-WORK.md](PARALLEL-WORK.md).

Shared registration, world, combat, ground/resource and SQL hooks have one active integration owner. Heavy full-suite/browser/build checks are coordinated in one verification lane. Each child is one understandable purpose, about 400 changed source/test/capture lines or deliberately split at the stated function boundary before implementation.
