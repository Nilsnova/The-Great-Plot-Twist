# Shared island Realtime membership

This bounded #501 security change protects fresh private-channel authorization for
persisted shared islands. Responsible teammate: Ianno Hollensteiner. Existing
place Broadcast policies let any registered player listen and send, even when
the island HTTP API rejects that player as a nonmember.

## Agreed behavior and scope

Replace both existing place-room SELECT and INSERT policies, preserving their
guest-admission, topic syntax and Broadcast-only gates. Known legacy island rooms
and other legacy places keep their current behavior. For a canonical island room,
look up the existing island code. Unknown or malformed island codes deny access.
Any persisted `island_economy_state` row makes that island private, including
paused state and irrespective of feature flags or account activity. Only the
island owner or an exact `island_members` row with `left_at IS NULL` may access it.
The rule covers rooms 1 through 99.

The internal predicate is
`island_realtime_private.may_access_place_topic(p_topic text) RETURNS boolean`.
It is STABLE, SECURITY DEFINER, has an empty search path, fully qualifies its
database references, and derives its actor only from `auth.uid()`. The new private
schema is not added to any exposed API-schema list. Only `authenticated` receives
schema USAGE and function EXECUTE; browser roles receive no new table rights,
schema CREATE, or actor-selecting overload. The helper reads only existing
islands, economy state and membership. It creates no authority provider, account,
assignment, table, or HTTP API. World Presence and crew policies are unchanged.

Migration filename was generated by the Supabase CLI:
`20261118192119_shared_island_realtime_membership.sql`. It must remain safe to
apply twice. This work adds that migration, focused disposable PostgreSQL tests,
and this spec only; no live database/settings changes are authorized here.

## Acceptance checks

- Under the actual `authenticated` database role and caller JWT, shared owners
  and active members can SELECT/INSERT Broadcast messages; outsiders and departed
  members cannot. Admission makes an existing legacy island private on the next
  authorization check, and departure denies the next fresh check.
- A paused shared account stays private. Known legacy islands, class harbor and
  other legacy place rooms retain access for registered/admitted guests. Anonymous
  guests still require existing class admission, including owners/members.
- Unknown/malformed island codes, invalid room numbers, missing actor, and wrong
  extension are denied. All five existing Realtime policies remain accounted for;
  no broader permissive SELECT/INSERT policy can OR around the shared rule.
- Assert helper owner/security/search-path/signature/grants, no browser CREATE or
  direct membership/economy-state/islands reads, and no caller-supplied actor.
- Apply the complete migration chain twice on local Unix-socket PostgreSQL and run
  the focused suite plus existing guest-policy checks. Run Ruff, migration parse,
  whitespace and secret checks and inspect the complete diff.

## Runtime boundary and remaining acceptance

Supabase caches Realtime authorization for an existing connection. This predicate
protects fresh joins and authorization refreshes; it does not evict an existing
subscriber after membership departure or legacy-to-shared admission. Canonical
admission/leave revocation or topic rotation remains a release prerequisite, and
HTTP/controller effects still need their independent current authorization.

After local integration, provider acceptance must verify the private schema is
absent from exposed API schemas, client channels use `private: true`, hosted
Realtime public access is disabled for these private channels, and actual fresh
owner/member/outsider joins behave as expected. Local stand-ins prove PostgreSQL
RLS and grants, not hosted cache behavior or provider configuration. Current
reference: https://supabase.com/docs/guides/realtime/authorization.

## Local verification

The new regression first failed because an outsider could SELECT a shared island
Broadcast row. With the migration, the focused shared-membership suite and full
existing class-code/guest-policy suite pass: **49 checks in 10.03 seconds**, using
the complete migration chain applied twice. Full backend Ruff passes, all **76**
migrations parse, and the diff has no whitespace errors. Independent source review
found no issue in this bounded fresh-authorization scope. Actual provider checks
and existing-channel revocation remain separate acceptance work.
