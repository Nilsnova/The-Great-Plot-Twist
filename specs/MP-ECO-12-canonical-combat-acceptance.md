## Lock admission

The existing shared repair transaction predates the canonical controller/profile lock chain.
An additive migration replaces only its lock admission: distinct signed-sorted actor and
island-owner Class 0 scopes, the original account selected by both ID and owner, the common
operation root, then sorted existing actor/owner profile anchors and optional personal Captain
rows before island/recovery/wave/structure locks. No account belonging to another owner is
locked. A missing actor profile refuses a fresh action and rolls back its root.

Owned receipt replay remains before current profile, membership, assignment, wave, HP, quote or
quota checks. Any member may repair; a personal Captain profile or active assignment is not
required. The existing signature, immutable fingerprint, frozen exact price, three shared
successes per accepted reservation, treasury child, HP/event/receipt atomicity and refusals
remain unchanged. No existing migration, wave function, authority provider or frontend changes.

## Actual source composition

Disposable PostgreSQL tests create initial legacy buildings and entitlements, then use actual
admission, personal conversion, controller attachment and accepted bell. The trusted test
template describes those actual buildings; the native bell freezes real identities, geometry,
Captain metadata and the common five-field economy origin. No replacement authority provider
or direct canonical slot/fall/hold/checkpoint updates may authorize a result.

Cover a real Tavern's bounded positive HP report during a stationary timed hold and free
completion. Cover actual sealed structure damage checkpoints, exact full-price shared repair
without an Engineer discount, actor-shared three-use quota, no private-wallet fallback, original
receipt after later damage, and rollback on event/receipt faults. Also prove a foreign account
row cannot be borrowed and concurrent deletion/global UID work cannot invert the approved locks.

These are synthetic accepted-report scenarios within the existing combat-report trust model.
They do not prove every simulated hit, authenticated browser gameplay or network liveness.
Realistic concurrent polling and report/completion latency remain separate integration checks.
No hosted migration, admission, activation or publication is authorized by these tests.
